# Карта функциональных разрывов

Этот слой строится поверх `analysis/subject-cards` и обрабатывает одну предметную карточку за проход.

Ключевой принцип: карта функциональных разрывов сравнивает бизнес-функцию, а не имена объектов текущей доработки. Специфичные реквизиты, табличные части и модули доработки описывают реализацию на текущей конфигурации; их отсутствие в целевом релизе является фактом целевой проверки, но не самостоятельным доказательством функционального разрыва. Перед выбором решения нужно проверить, закрывается ли тот же бизнес-смысл типовыми средствами целевого релиза: настройками, дополнительными реквизитами и сведениями, маршрутами, правами, связями, регламентными заданиями или изменением процесса.

Базовый цикл:

```bash
python -m one_c_autoresearch functional-gap build --card <slug>
python -m one_c_autoresearch functional-gap refresh --card <slug>
python -m one_c_autoresearch functional-gap inspect-target --card <slug>
python -m one_c_autoresearch functional-gap dashboard-build
python -m one_c_autoresearch functional-gap validate --card <slug>
python -m one_c_autoresearch functional-gap map-build
```

`build` создает черновик gap-карточки, `refresh` обновляет generated-поля без перезаписи ручных решений, `inspect-target` ищет аналоги в целевом релизе, `dashboard-build` собирает статичный экран ревью, а `validate` проверяет доказательность и открытые вопросы. Для `build`, `refresh` и `inspect-target` флаг `--force` разрешает принудительную регенерацию ручных или заблокированных аналитиком полей; без него зафиксированные решения и curated target-analysis не перетираются.

Поведенческие проверки целевого релиза включаются только при явном профиле. Укажите профиль в `project.toml`:

```toml
[functional_gap]
target_profile = "target"
```

Профили лежат в `analysis/functional-gaps/profiles/<id>.toml`. Начните с `_templates/target-profile.toml`, затем замените идентификаторы и evidence-правила под конкретную целевую конфигурацию. Не переносите профиль из одного проекта в другой без проверки исходников целевого релиза.

Назначение слоя: для каждой предметной доработки отдельно зафиксировать гипотезы перехода на целевой релиз, обязательные проверки и решение аналитика.
